## バグ修正(コミット ded54c6)

**現象**: `all goroutines are asleep - deadlock!`(size 10 / 16 コアで再現)

**根因**: `split()` が実セル(1..len-2)ではなく配列全体(境界セル込み)を対象にループしていた。
結果として、

1. 右境界セル(www)を start とする切片が生成される → slice 長 2 → interior 空
2. interior 空 → `firing()` がいつも真 → goroutine は t=0 で「発火済み」として即退出
3. 隣接 goroutine は退出を知らず、バッファ 1 のチャネルに送り続けて詰まる → 全停止
4. また `NumCPU >= size+2` のとき n=1 となり最初の切片 `[0:2]` も空になる

**症例**: 7 コアに偽装すると size 11/14/17/23/29 のみデッドロック(切尾の位置ずれが slice 長 2 を作るアライメント)。
それ以外は常に正確に 2n−2 で発火 → 中身のダブルバッファ+チャネル同期の設計自身は正しい。

**修正**: 実セルだけを対象に分割し、各 goroutine が最低 1 実セルを interior に持つ(slice 長 >= 3)よう保証。
検証: size 2〜128 全部で全セグメント同一の t=2n−2 で発火。

### 実装メモ(並列設計の要点)

- 実セルの所有権は排他的。各セグメントは「左隣 1 セル + 実セル群 + 右隣 1 セル」の slice を持つ。
- 二重バッファ(cur/nex)は全セグメントで共有し、各ステップ終了後 1 つずつ隣トークン交換(送信2+受信2/ステップ)。
- トークンはメモリバリアでもある: 自分の次ステップの境界読み取りは、隣の same-step 書き込みの後に行われる。
- 外部セル(www)は初期化後に誰も書かない → どのレベルで読んでも常に有効。

### v5(k=2 バッチ)が成立しなかった理由(設計上の欠陥)

単一セグメントでは全 size 正しく同期するが、複数セグメントで全滅。本体:

- バッチ内 j=0 が担当外のハロセル [Lo-1, Hi+1] を書き込むため、**同じ物理バッファに異なるレベルの値が別セグメントから同時書き込まれ衝突**する(例: 自分の j0 が cell lo-1 を level B+1 で、左隣の j1 が同じ buffer の同じセルを level B+2 で書き、後勝ちが非決定的)。
- 逐次ステップ版(v1/v2)は所有権排他でレベル書き込みが 1 対 1 なので問題ない。**「halo を書く = 書き込み所有権の排他性が崩れる」**ことが本質。
- 修正には私的配列 + 境界値のメッセージ交換が必要で、メッセージ数はむしろ増える(halo 幅ぶん)。得るものがない → 却下確定。

### SIMD 検討(2026-10-13、rust スクラッチプロトタイプ実測)

内側ループは `idx = (l<<8)+(c<<4)+r` のランダムなテーブル参照が本体で、ベクタ化には **AVX2 gather(vpgatherdd、scale=1 のバイトオフセット参照)** を使う。表は u8 配置のまま(8KB、L1 常駐)、gathered dword の下位バイト = 状態を回収。u8 化(セル・表とも)は AVX2 の前提でもある。

スクラッチ(`/tmp/fssp-simd`、sequential・同期なし、合成ルールでバリアント間の進化バイト等価チェック済み):

| 変種 | per-op | 備考 |
|---|---|---|
| usize スカラー(現行と同形) | 1.03ns | 1 op ≒ 4.3 cycle |
| u8 スカラー | 1.03ns | **効果なし**(メモリは既に全キャッシュ内、律速は計算側) |
| **AVX2 gather (u8)** | **0.235ns** | **4.4x**(≒ 1 cycle/cell、n=20k〜200k で一定) |

- **リポジトリ rust への組み込み完了(2026-10-13)**: 全セル `usize → u8`(パーサ・fired・new_line/first_line も)、ルール `[u8; 8192]`、`simd::step`(32 セル chunk + scalar tail)を `nextline_par` に導入。`is_x86_feature_detected!("avx2")` を main で 1 回判定してフォールバック(スカラー)を保持。size 2..64+256 全通過、size 10 の最終状態は ruby と一致。

golang(4.29s @100k、16.6s @200k)に対して rust AVX2 は **2.3〜3.1x**。この規模では計算 ≈ 0.4s、同期 ≈ 0.9s+ と同期が再び主要因になりつつある(次の最適化対象)。
- 32 セル/chunk の構成: 3 loadu + unpacklo/hi×3 + idx 計算(slli/add) + 4 cvtepu16 + 4 gathers + 対応づけ(shuffle+and)4 + half 内詰め(extract+bslli+or)→ 32B storeu。末尾は scalar。
- AVX-512(zmm gather、16レーン/inst)はこの CPU(Tiger Lake)で可用だが 512bit 演習時のダウンクロックがあり、AVX2 版を先に採るのが無難。Rust は stable intrinsics(`std::arch::x86_64`)で足りる(nightly 不要)。
- スクラッチの main.rs はバッチの検証用として残すこと(リポジトリ外)。

### rust の -d(ダンプモード、2026-10-13 追加)+ -c(色付き)

`fssp.exe [size] -d`: 1 ステップごとに途中経過を出力。**ruby の `-d` とバイト完全一致**する書式(名前を | 連結・色なし、size 2/3/4/5/10/15/17/23/40 で diff 検証済み)で、ruby ↔ rust の直接突き合わせ検証に使える。ダンプモードは逐次実行(並列はステップ同期の中に全体を一つのタイミングで参照できる地点がないため)。並列パスの変更はなし。

`-c` / `--color`: dumpln と同じ 24bit ANSI 色(ルールファイルの前/背景色)でダンプする。-c 単独は -d を兼ねる。プレーンな `-d` は diff 検証用にそのまま維持。

### rust のルールファイル指定 (-r / -s / -h、2026-10-13)

`fssp.exe -r ../mazoyer.rul.txt [-s size] [-d] [-c]`。**ルールファイルは必須**(既定値は持たない)。セル数も `-s` / `--size` のオプションにした(既定 10)。位置引数は取らない。`-r` / `-s` は値を取るので引数ループを `for` から index の `while` に変更。golang/ruby は未対応。

- `-r` なし / 値なし → `rule file is not specified` / `-r: value is required` + usage を出して exit 1
- 解釈できない引数 → `unknown argument: ...` + usage を出して exit 1。`-s` に非数値 → `-s: invalid size: ...`
- `-h` / `--help` → usage とオプション一覧を **stdout に** 出して exit 0(エラーではないので stderr には出さない)。他の引数と併用しても help が優先。usage の複数行文字列は `\` による行継続だと次行の先頭空白が食われるので `concat!` で組んだ
- 開けないファイルはパスを含めたエラーを出す(従来はパスを含まないメッセージだった)

**なぜ必須にしたか**: 従来は数値に解釈できない位置引数を黙って捨てており、既定の waksman で走っていた。このため `fssp.exe balzer.rul.txt 5 -d` と打つと**何の警告もなく waksman が走り**、balzer が発火したように見える紛らわしい事故になった(実際に起きた)。既定を持たせないことでこの事故の余地自体をなくした。

リポジトリ直下に `mazoyer.rul.txt`(7状態/120規則)と `balzer.rul.txt`(9状態/182規則)を追加(出所: consoleCAS-SL1 の `app/*.rul`、MIT、改行は既存と同じ CRLF)。`mazoyer` は**無改造で size 2..40 すべて 2n-2 で発火**し、`rust -d` の出力が ruby `-d` と一致する(size 2..64 で確認)。SL1rule 形式のパーサは元から汎用だったことがこれで確認できた。

`balzer` は上流のファイルのままでは size 5,9,17,33,34 で未登録規則を引いていた。**発火状態 F を左辺に持つ規則が 1 つも無く**、途中で F が隣に現れるため(例 size 5: t=7 が `M M M F F`)。未登録の扱いが実装ごとに違う: golang/rust は状態0(= balzer では A)にフォールバックして**黙って誤動作**、ruby は nil でクラッシュ。general 位置を右端にすると第 1 ステップの三つ組 `(www, L, L)` が未登録で全サイズ即落ちする(このファイルは左端前提)。

**修正(2026-10-13、ルール表 1 行)**: `R ##B ##M` の遷移先が `Q` だったのを `A` に直すと全サイズで解決した。`C ##B ##M ->A` と揃う形なので上流側の転記ミスと思われる。修正後は ruby 参照実装で size 2..40、rust で size 2..60 に加えて 100/101/128/256/1000/10000 がすべて 2n-2 で発火し、**発火状態が最終ステップより前に一度も現れない(厳密な同時発火)**ことを確認。`rust -d` と `ruby -d` の出力も一致する。したがって未登録規則の扱い(吸収状態にする / エラーにする)を変える必要はなくなった。

### 調査中に見つかったその他事項

- **size=1 は仕様外**: ルールセットに `www ##P0 ##www` が存在しない。ruby は nil 演算で crash、golang は未定義ルール→Q で無限ループ。バグではなくルール表の対応範囲。
- ruby のパーサは `split(/(?:##|->)/)` で**末尾スペースごと名前を比較**しており、ルール行に付いている同一幅の余白(例: `Q    ##Q    ##Q    ->Q    `)と偶然整合する構造。golang は空白を剥がして比較しており、同じ結果になる。
- **rust 修復済**(2026-10-12): E0106(`Vec<AryPair<'a>>` ライフタイム)+ 未使用 import 整理 + `split()` を golang 修正と同じ不変則(実セルのみ対象 / interior ≥ 1)に書き換え。設計は golang と同じく二重バッファ共有 + mpsc トークン(rayon 論理 16 スレッド、チャネルは unbounded)。最終状態の fired チェックを main に追加(size 2..64 全部通過、size 10 の最終状態は ruby と一致)。
- **同期しないルールセットを並列実行すると rust が `RecvError` で panic する問題を修正**(2026-10-13、`-r` 導入で到達可能になった経路)。`balzer.rul.txt` の size 5 で再現。`par_simulate` の各セグメントが**自分のスライスだけで `fired()` を判定して早期離脱**するため、先に全セル F になった側が抜けて、隣が `r.recv()` で詰まる。waksman は常に同期するので今まで表面化していなかった。
  - **修正**: セグメント単位の fired をやめ、**全セグメントを固定 2n-2 ステップ回し、判定は最後に main で 1 回だけ全体に対して行う**形にした(2n-2 は FSSP の下限なので正しい解は必ずそこで発火する。golang の v1 実験と同じ形)。あわせて、2n-2 が常に偶数であることから swap 回数が偶数に戻り、最終状態が `cur` 側に載って main の `fired(&current)` が正しく効く(従来はステップ数が奇数のとき古いバッファを見ていた)。
  - **検証**: `balzer` の size 5,9,17,33,34 が panic せず `NOT SYNCED` を出すようになった。waksman / mazoyer の最終状態は debug ビルドのダンプで変更前と完全一致(size 2..1000、101 以上は並列パス)。性能は 100k で 2.20s → 1.90s(発火スキャン廃止ぶん)、200k は 5.63s / 5.59s で有意差なし。
  - 残: 逐次 `-d` 側の上限判定が `t <= 2n-2` なので、同期しない入力では 1 ステップ余分に進む(未修正。同期する入力では `fired` で先に抜けるため影響なし)。

## 教訓

- `split()` 的な区切り処理は「interior が空にならないこと」を不変則として明示的に保証する(今回の不具合はここに全部落ちていた)。
- バッチ化(一時ブロッキング)は「書き込み所有権の排他性」を崩すと破綻する。halo を書く設計には私的配列+値交換が必須。
- 実験バイナリのビルド実行は毎回ディレクトリを明示すること。cd のリセットで**別バイナリの数値を測って報告してしまう事故**が実際に起きた(v5 初回)。
